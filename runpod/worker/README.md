# Loom RunPod serverless worker

Deploys Loom's **Anima** image pipeline to a **serverless** RunPod endpoint —
auto-scaling, no persistent pod, pay only per render. The worker image carries
the custom nodes (Impact-Pack + Subpack + Easy-Use); a **network volume** carries
the ~6.4 GB of Anima weights (one DiT, its CLIP/VAE, the 3 Anima LoRAs, and the
FaceDetailer SAM/YOLO detectors).

You only do this once. Updating weights later = re-run the upload script (or the
`--add`/`--rm` flags for a single LoRA — no rebuild); changing the custom-node
set = re-run the generator, then rebuild & re-upload. **Models and LoRAs are
never baked into the image**, so adding/removing them never requires a rebuild.

```
runpod/worker/
  gen_worker.py          SCANS your workflows -> writes the 3 files below
  Dockerfile             (generated) custom worker = blib-la base + the union of node packs
  extra_model_paths.yaml (generated) points ComfyUI at /runpod-volume for all weights
  models_manifest.json   (generated) every model file -> its volume key
  upload_models.py       pushes the manifest's files to the volume over the S3 API
                         (+ --add/--rm for single LoRAs, no full regen)
  build.bat              one-shot docker build+push
  .dockerignore
```

The three generated files come from `gen_worker.py`, which reads `workflows/*.json`,
figures out which custom-node repos and model files they need, and writes a SINGLE
image + volume layout that runs **all** of the scanned workflows. The current default
set is the Anima family — one endpoint serves `anima`, `anima_background`, `anima_cutout`.

---

## Step 0 — Generate the artifacts

```bash
# Anima family only (the default for this worker):
python runpod/worker/gen_worker.py anima_basic_api anima_background_api anima_cutout_api
# all workflows/*.json:
python runpod/worker/gen_worker.py
# resolve any unknown custom nodes via ComfyUI-Manager's DB:
python runpod/worker/gen_worker.py --online
```

It prints which node repos it picked, the model dirs, and flags anything it
couldn't find locally or resolve. It also reports any **IGNORED** weight-looking
value that isn't on a real loader input (a phantom field that would otherwise
bloat the volume). Re-run it whenever you add or change a workflow.

---

## Step 1 — Build & push the worker image

You need a Docker Hub (or any registry) account. From this folder:

```bash
cd runpod/worker
set IMAGE=YOURUSER/loom-comfy-worker:1.0
build.bat
```

`build.bat` wraps `docker build --platform linux/amd64 --build-arg BASE_TAG=3.4.0-base -t %IMAGE% .`
and pushes. Override `BASE_TAG` to pin a newer `runpod-worker-comfy` base
(check https://hub.docker.com/r/timpietruskyblibla/runpod-worker-comfy/tags).

Or manually:
```bash
docker build --platform linux/amd64 -t YOURUSER/loom-comfy-worker:1.0 .
docker push YOURUSER/loom-comfy-worker:1.0
```

> Rebuilds are only needed when the **custom-node pack set** changes (e.g. you add
> IPAdapter). Swapping checkpoints/LoRAs/VAEs does NOT need a rebuild — those live
> on the volume. `sync.py` detects the node-set change automatically.

---

## Step 2 — Create the network volume

RunPod console → **Storage → Network Volumes → New**.
- Pick a **datacenter that supports the S3 API** (e.g. `EU-RO-1`, `EUR-IS-1`, `US-KS-2`).
- Size: **20 GB** is plenty for the ~6.4 GB Anima set with headroom.
- Note the **volume id** and its **datacenter**.

---

## Step 3 — Upload your models to the volume (no pod)

RunPod console → **Settings → S3 API Keys → Create** (gives an access key + secret).

Put these in the project `.env` (gitignored):

```
RUNPOD_VOLUME_ID=<volume id>
RUNPOD_S3_DATACENTER=US-KS-2
RUNPOD_S3_ACCESS_KEY=<s3 access key>
RUNPOD_S3_SECRET_KEY=<s3 secret>
```

Then:

```bash
pip install boto3
python runpod/worker/upload_models.py --check   # dry run: verify local files + plan
python runpod/worker/upload_models.py            # upload (skips files already there)
```

The file→key map lives in `models_manifest.json` (regenerated by `gen_worker.py`);
it matches `extra_model_paths.yaml`. Run `gen_worker.py` again when a workflow
needs new weights, or use `--add`/`--rm` for a single LoRA (see below).

---

## Step 4 — Create the serverless endpoint

RunPod console → **Serverless → New Endpoint**.
- **Container image:** `YOURUSER/loom-comfy-worker:1.0`
- **Network volume:** attach the one from Step 2 (it mounts at `/runpod-volume`).
- **GPU:** 24 GB (e.g. RTX 4090 / A5000) is comfortable for SDXL + FaceDetailer.
- **Container disk:** 20 GB. **Max workers:** to taste. **Idle timeout:** low (5 s) to save cost.

Copy the new **endpoint id**.

---

## Step 5 — Point Loom at it

In `.env`:

```
RUNPOD_ENDPOINT_ID=<new endpoint id>
```

(or set `runpod.serverless_endpoint_id` in `user.yaml`). Loom's batch renderer then
fans jobs out to it automatically — see [runpod-serverless memory] and
`loom/server/services/batch_images.py`.

---

## Step 6 — Verify with your REAL workflow

```bash
# inspect the exact graph that will be sent (no API call):
python test_serverless.py --dry-run --model illustrious --prompt "1girl, red dress, city street BREAK night, neon lights"

# real render against the endpoint — writes PNGs to runpod_test_output/:
python test_serverless.py --endpoint <endpoint id> --model illustrious \
  --prompt "1girl, red dress, city street BREAK night, neon lights" --latent 832x1216
```

A success writes a PNG and prints its path. If a node or model is still missing,
the worker returns the exact ComfyUI error (e.g. `Node 'X' not found`,
`ckpt_name not in list`) and the test prints it — fix that one item and re-run.

## Adding / removing a single LoRA (no rebuild)

LoRAs live on the volume, and the workflow graph that names a LoRA is sent
per-request by the serverless provider — so adding or removing one never needs
an image rebuild or a full `gen_worker.py` regen. Use the single-file flags:

```bash
# add: upload one LoRA from your local ComfyUI models dir and register it
python runpod/worker/upload_models.py --add loras/my_new_lora.safetensors

# remove: delete it from the volume and the manifest
python runpod/worker/upload_models.py --rm  loras/my_new_lora.safetensors
```

`--add` takes a path relative to your ComfyUI models dir and infers the volume
key from the subdir (`loras/` → `models/loras/`, etc.). After `--add`, reference
the filename in a `LoraLoader.lora_name` node in your workflow and it resolves on
the next render. After `--rm`, make sure no workflow still references it.

To add many at once, or to refresh the whole set from current workflows, just
re-run `gen_worker.py` + `upload_models.py` as in Steps 0/3 — the manifest is
idempotent (deduped by volume key).

## Image-preset LoRAs (auto-imported from Civitai)

Image presets (`configs/image_presets.json`) are named LoRA stacks injected into
the workflow at **render time** — they are NOT in any workflow JSON, so the
`gen_worker.py` workflow scan can't see them. They're handled separately:

- **Source map:** `configs/civitai_loras.json` maps each preset LoRA's bare name →
  its Civitai model **version id** (the public Anima base-v1.0 artist-style packs).
- **Local download:** on app start, `startup.download_preset_loras` fetches any
  preset LoRA missing from your ComfyUI `models/loras` (background thread). It needs
  a Civitai API token — set `CIVITAI_API_TOKEN` in `.env` (the Civitai download
  endpoint returns 401 without one). No token → it silently skips. You can also run
  it standalone via `loom.comfy.civitai.ensure_preset_loras(root, loras_dir)`.
- **To the volume:** both manifest generators (`gen_worker.py` and the app's
  startup regen) now **fold preset LoRAs into `models_manifest.json`** — so the
  normal `upload_models.py` (Step 3) ships them to the volume alongside everything
  else. The worker reads them from the volume at render time; **no Civitai token is
  baked into the image**.

So the end-to-end flow is:

```
CIVITAI_API_TOKEN in .env  ->  restart app (downloads LoRAs locally)
  ->  python runpod/worker/upload_models.py   (ships them to the volume)
```

Use `upload_models.py` directly here — not `sync.py` — unless the custom-node set
actually changed, since `sync.py` also regenerates the Dockerfile.

## Cost / scaling notes

- Serverless bills only while a worker is running a job; idle timeout returns it to zero.
- First request after idle has a **cold start** (~1–2 min here) while the worker boots
  and loads the checkpoint from the volume. Warm requests are fast.
- For big casts, Loom fires N jobs concurrently only when that workflow was selected
  for RunPod. The client cap is `runpod.max_instances`, which should match the
  endpoint's `workersMax`. `deploy.py` reads `runpod.min_instances`,
  `runpod.max_instances`, `runpod.idle_timeout_s`, and `runpod.queue_delay_s`
  from `user.yaml`; re-run it with `--update-existing` after changing them.
  Otherwise jobs will just wait in RunPod's remote queue.
